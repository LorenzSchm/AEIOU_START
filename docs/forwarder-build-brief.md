# Build the autonomous 5U air freight forwarder

## Instructions for the implementation chat

Implement the backend described here in the AEIOU_START repository. Use Java 21, Spring Boot, and Maven. The companion file **forwarder.openapi.json** in this directory is the public contract for a separate frontend developer. Deliver a working backend, persistent worker, demo data, replay simulator, live integration adapters, automated tests, and concise run instructions. The frontend developer owns the browser application. Publish the contract and make every operation callable in demo mode. Work through the build and verification steps below rather than returning another design document.

The repository already contains ten airline tariffs, a carrier directory and pickup zones under start-kit. Read those files. Treat the team kit card and local environment as confidential. Preserve existing project files and keep credentials out of commits, fixtures, logs, API responses and generated clients. Start with the demo profile. Live mailbox sends, bookings and paid requests belong only to the explicitly selected live deployment. Demo and tests must work offline with zero credentials.

**Definition of success.** A new RFQ arrives while previous shipments are awaiting confirmations. The system reads it, prices the requested service, sends one timely quote in the correct thread, books on acceptance, confirms to the customer, and later answers a tracking question from its CRM. No person has to approve, select, retry or resume a routine or exceptional case. A person can choose to intervene in a session. The UI can explain a quote down to the tariff row, portal response or bid that supported it. Restarting the backend preserves both work and decisions.

## 1. Competition behavior and priority

| Constraint from 5U | Implementation consequence |
|---|---|
| One air export RFQ about every six minutes, expiring six minutes after receipt | Use the organizer message timestamp for the deadline. Drain backlog promptly after restart. A late-discovered message does not receive a new six-minute clock. |
| First quote in the customer thread counts. One requested option with one all-in total and currency | Send one decision with a validated recipient, parent ID, route, service, transit and price. Avoid interim customer acknowledgements that could consume the first response. Keep bid solicitations in carrier correspondence. |
| Customer chooses cheapest or fastest. Carrier bids also have a 50/50 price and speed rule | Keep carrier-bid ranking and customer objective ranking as independently testable policies. The exact normalization has not been published in the sources used here. Version the assumption described in section 5. |
| Only accepted quotes score. Acceptance is within 5% of the benchmark | Measure official acceptance. Never manufacture a benchmark or reduce a quoted price below a supported offer. No margin is in scope. |
| Up to 45 points for accuracy, 40 for gateway cost, 15 for speed. Full time points within two minutes, zero at six | Use the first two minutes intelligently. Gather rates in parallel. Keep an explicit reserve for validation and sending. |
| Each quote needs a gateway call for cost credit. The hourly spend per accepted quote affects points, reaching zero cost points at USD 0.10 | One small useful gateway extraction is the routine RFQ path. Log usage per action and hour. A local outage fallback may still produce a verified quote; record its missing gateway credit. |
| Acceptance, booking and confirmation are distinct. First tracking answer counts and can earn up to 10 points per booked shipment | Keep independent state for each stage and each tracking question. Use actual confirmed records in customer replies. |
| Conditions change during the event. Technical depth, UX and email quality matter | Handle fresh tariffs, currency changes, rate limits and alternative booking channels. Keep historical decisions reproducible and show how the chosen offer beat its alternatives. |

Source inputs are the organizer challenge brief and deep dive dated 21 November 2026, the Discord clarification on tracking supplied by the team, the starter kit, and the organizer's public API schema. The numeric time targets below the two-minute scoring threshold, model targets and ranking tie-breaks are team design defaults. Keep them configurable and version the policy used on each decision.

## 2. Runtime and boundaries

Build one deployable Spring Boot service. Use a compatible pinned Spring Boot release, Maven Wrapper, Spring MVC, Jackson, Flyway, JDBC and PostgreSQL. Choose PostgreSQL for transactional cursor updates, unique effect keys, durable timers, row-level locks and coherent read snapshots. Provide a Compose setup with a persistent database volume. Use JUnit 5, Testcontainers PostgreSQL, and stub HTTP servers for upstream contract tests. Use java.time.Clock everywhere that affects a decision, BigDecimal for all freight quantities and monetary arithmetic, and bounded asynchronous I/O. A worker waiting on a carrier must release its thread and persist a wake-up time.

| Java package boundary | Public responsibilities |
|---|---|

| ports | Mailbox, attachment store, rate portal, gateway, result board, clock, repositories, simulator input. External DTOs stay inside the adapters. |

| infrastructure | Database migrations, poll cursor, job leases, scheduled wake-ups, inbox/outbox, event sequencing, spend and rate-limit accounting, health checks. |
| api | Operations and DTOs matching the OpenAPI file, optional session controls, timeline, evidence, replay and stream. REST controllers never perform upstream calls on a dashboard read. |

The organizer's router and three specialists map to an inbox router, an RFQ/booking workflow, a tracking workflow and a tariff-ingestion workflow. Give each a typed input, a bounded set of actions, and persisted state. An LLM extracts facts and can phrase exceptions; the workflow owns identity, recipients, timers, price arithmetic and permission to send.

## 4. Intake and extraction

1. Persist every incoming message before parsing. Route RFQs, corrections, acceptances, rejections, carrier bids, desk replies, tariff files, booking confirmations, tracking questions and unknown mail. A message may contain several kinds of evidence. Process each relevant part exactly once locally.
2. Prefer trusted identifiers in this order: known upstream parent/references chain, booking or team reference with matching participant, then an unambiguous pending solicitation to that sender. Subject and sender alone are insufficient when two shipments share a lane. Hold unmatched evidence for later automatic correlation without blocking other cases.
3. Extract customer language, requested objective, scope, airports, pickup address and postal zone, piece groups, dimensions and units, gross weight with its scope, total volume, date/time with timezone, cargo constraints and explicit deadline. Represent absent, conflicting and known values separately. The input text is data; email text cannot select tools, set pricing policies or override recipient allowlists.
4. A fact carries the original phrase, document/cell/page or message position, normalized value, time observed and revision. Keep high-value alternatives such as per-piece versus total weight. Parse decimal commas, thousands separators, pounds, inches, centimetres, cubic metres, local dates, multilingual negation and quoted thread history. Use deterministic unit conversion after extraction. Do not count both an explicit total and its components.
5. A customer correction creates an immutable revision. Invalidate old open candidates that depended on the changed facts. Responses to an older solicitation attach to its revision. A correction after first send cannot create a second scored first quote. Handle a requested amendment as separate correspondence linked to the original.
6. If two interpretations produce the same eligibility, service, transit and all-in amount, the workflow can proceed with the shared result. If the difference is material, inspect attachments or relevant thread evidence first. A customer clarification is an autonomous exception path only when it can arrive in time and the protocol permits it without spending the first scored response. Otherwise log the precise unresolved reason by deadline. Never invent a commitment.

## 5. Deterministic pricing and sourcing

**Start all independent work together.** Read local active tariffs, discover applicable portal offers and solicit the 2–5 eligible airline counterparties specified for the request where available. Select recipients by destination and coverage from the supplied directory. Where fewer eligible counterparties exist, record coverage rather than contacting unrelated addresses. For door pickup, look up the supplied pickup zone/origin mapping and request an eligible trucker offer in parallel. Give every solicitation a stable local ID, shipment revision and expected reply type. Cap concurrency and share quotas across sessions.

**Compile tariffs once.** Use POI for workbook and DOCX content, PDFBox for PDF text and layout, ordinary parsers for TXT/CSV, then OCR or vision for unreadable tables and images. Join the two Danube image pages into one logical tariff when their metadata agrees. Preserve row coordinates and original numeric tokens. A normalized tariff includes issuer, lane, currency, validity window, volume factor, minimum, breakpoints, rates, transit, surcharge basis, rounding and exceptions. Deduplicate by bytes plus parser version. Check for duplicate/conflicting lane rows, missing units, invalid break order and partial pages. Activate valid rows atomically. For ambiguous rows, try a second extraction or independent source automatically. Mark unresolved rows unusable. Preserve prior versions for replay and honor their validity dates.

**Calculate with explicit units.** Sum volume across piece groups. Compute chargeable weight using the applicable tariff rule. For the provided Yellowtail tariff, chargeable kg is the larger of gross kg and volume in cbm times 167. For each permitted billing basis, compute freight as the larger of the freight minimum and billed kg times the applicable rate. Add fuel and security using their own billing basis. Where paying at a higher breakpoint is permitted, evaluate its complete cost including surcharges and retain both actual and billed weight. Keep the physical manifest factual. On the portal, use documented semantics and confirm purchasability before treating an alternative billing basis as bookable. Never hard-code breakpoints across airlines.

**Assemble complete options.** A candidate has a set of legs, feasible constraints, provider, transit, total in source currency, comparison total, expiry, booking instructions and evidence. Include pickup, handling or other costs when required by the actual request and rate. An inclusive portal or email price already covers its stated components. Avoid duplicate surcharges. Convert comparison amounts only with evidenced applicable FX. For the documented portal USD case, multiply USD by EUR per USD, preserve the original currency, record the FX source and use consistent rounding. Treat missing FX or required pickup cost as an incomplete comparison. Preserve published precision and round at the rule-defined stage. Serialize decimals as strings to the UI.

**Rank feasible offers.** Eliminate wrong route, scope, expired rates, unsupported cargo, capacity or deadline violations, unknown required charges, and offers without a supported path to booking. For customer cheapest, sort by all-in comparison total and then transit. For fastest, sort by complete comparable service time and then total. Break ties deterministically by stable provider and offer ID. Avoid promising door-to-port transit when only the air leg is known. For the carrier-bid rule, start with a versioned policy that normalizes comparable bids' cost and transit within each eligible bid set using min-max, scores 0.5 of each, uses zero for an equal-valued axis and keeps the lowest score. Enter that bid winner alongside applicable tariff and portal candidates for customer-objective selection. Keep all raw offers and test alternate interpretations via replay against official outcomes. This ordering and normalization are explicit assumptions.

**Illustrative arithmetic fixtures from the real Yellowtail MUC–LAX sheet.**

| Input | Expected result |
|---|---|
| Airport-to-airport, 100 kg gross, 0.2 cbm, November validity | Chargeable 100 kg. Freight EUR 173.00, fuel EUR 117.00, security EUR 14.00. All-in EUR 304.00. |
| Same lane, 20 kg gross, 0.05 cbm | Freight minimum EUR 82.00 applies before surcharges. Fuel EUR 23.40, security EUR 2.80. Total EUR 108.20. |
| Two pieces, each 120 × 80 × 100 cm, 150 kg gross total | Volume 1.92 cbm. Volumetric weight 320.64 kg before any stated rounding. Calculate from two pieces; preserve the original 150 kg gross total. |
| 99 kg billed at the ordinary MUC–LAX bracket | Ordinary basis costs EUR 355.41. If the governing offer explicitly permits billing at 100 kg, that alternative costs EUR 304.00. Test a second fixture where the alternative is prohibited. |

## 6. Scheduling, booking and durable effects

Persist a timer at intake, recompute on every relevant event and lease due jobs after restart. Defaults for the demo are a normal decision wake-up at 90 s, a full-speed target before 115 s, and a last dispatch target at 340 s of the 360 s RFQ window. Derive UTC instants from organizer receipt. Adjust the reserve using measured tail latency. A completed, demonstrably winning offer can go sooner. Wait only for a named dependency with a wake-up and bounded benefit. If a complete option exists at the last safe send, select the best eligible option. If none exists, close with an explicit reason. Keep sourcing, booking and tracking independent so one timeout never freezes the inbox.

| Situation | Transaction and resulting state |
|---|---|
| New RFQ | Create RECEIVED, transition to SOURCING, enqueue extraction/sourcing and deadline wake-ups. Control starts AUTO. |
| Ready to quote | In one transaction lock the case, recheck revision, pause flag, deadline and candidates, persist immutable quote decision plus unique outbound intent. Mark QUOTED on confirmed send; expose QUEUED or UNCERTAIN while delivery is unresolved. |
| Acceptance or rejection | Match the exact quote and customer. Acceptance advances QUOTED → ACCEPTED → BOOKING. Rejection closes the case. Late or duplicate mail updates evidence without duplicating effects. An acceptance that proves delivery can reconcile an uncertain send. |
| Portal booking | Reuse exactly the same rate_id/team_reference on transport retry. On expiry refresh the matching offer and verify service, currency and terms. Changed material terms require a customer-facing amendment through the supported workflow. A 409 belongs to reconciliation, never to a blind new booking attempt. A definitive 503 can trigger the documented airline-email fallback. |
| Confirmation | Store provider acknowledgement, then confirmed booking reference and milestones from the matching airline mail. Confirm to the customer once. Track the confirmed shipment in BOOKED. Preserve both the original quote and actual booking price for audit. |
| Tracking question | Resolve booking by reference and participants. Sort events by effective time with observed time as a tie-breaker. Answer the question once in the requesting thread using confirmed, estimated or scheduled terminology. If records are insufficient, seek the missing evidence and schedule a bounded follow-up. A factual last-known status is preferable to an invented location. |
| Deadline or unresolved material data | Close unquoted work with a reason. Continue ingesting late evidence for audit and learning. Capture official board verdict separately. |

**Mail delivery guarantee.** Assign unique local effect keys for the first quote per customer RFQ thread, one acknowledgement per booking, one tracking answer per question and one solicitation per target/revision. An outbox worker leases and fences work, records the attempt before I/O and stores the upstream ID on successful response. An interrupted request after possible transmission enters UNCERTAIN. The public API exposes no general sent-mail listing or documented mail idempotency token. Use known message IDs, inbound references, acceptance, confirmation or board evidence to reconcile when possible; never automatically transmit a second scored first reply on ambiguous delivery. If reconciliation remains impossible, record the unresolved outcome and continue all other cases. Portal booking retries have stronger upstream semantics. Include both crash windows in tests.

**Optional intervention.** PAUSE prevents new external dispatch for that session while evidence and timers keep arriving. A command cannot recall an action already handed to transport. Expose that fact in the timeline. SELECT_CANDIDATE is permitted only for a paused SOURCING session with a complete, current offer. It pins that offer and records the operator reason. RESUME revalidates expiry, revision and budget before dispatch. A paused RFQ still expires on organizer time. Optimistic concurrency and idempotency apply to all commands.

## 7. Token budget and learned timing

For a normal RFQ, make one small 5U gateway call that returns schema-validated shipment facts, evidence spans, objective, language and ambiguity flags. Include only new customer text, relevant attachment excerpts, and previously established fields affected by this message. Strip quoted thread history after preserving genuine amendments. A routine extraction should aim for at most 1,200 input and 350 output tokens; these are adjustable operating targets. Chunk unusually long inputs by relevant sections and account for every additional call. Record model, prompt version, latency, input/output tokens, purpose, shipment revision and reported cost or explicitly labeled estimate. Missing cost is unknown. Avoid central prompts containing all tariffs or all previous mail.

Use templates for known carrier solicitations, routine natural-language quotes, booking confirmations and common tracking answers. Localize salutations, units and the one all-in total. A rendered outbound validator checks recipient, reply parent, selected service, numeric amount, currency and absence of a second option. An exceptional gateway wording pass gets the immutable structured figures as input and goes through the same validator. If it changes a figure, fall back to the validated template. Cache attachment extraction by hash/parser version and message extraction by ID/content/prompt version; do not skip the required live RFQ gateway usage by replaying an unrelated cached response.

Allow one bounded additional read when a **specific material uncertainty** remains and new evidence can resolve it. On model timeout, malformed output or rate limiting, use previously verified fields, deterministic parsers and a budgeted retry if time permits. A failure never grants permission to fill an unknown price. Track gateway spend in each UTC hour divided by officially accepted quotes. Show an unknown ratio when there are zero accepted quotes. An initial engineering target is under USD 0.01 per accepted quote. Measure cost, accepted volume and latency together so fewer calls cannot hide worse results.

After the baseline works, build the token-free **wait-for-bid predictor** in Java. Persist request timestamp, eligibility, carrier/lane, elapsed time, competing offer, eventual bid arrival and whether that bid would improve the customer's objective. Continue collecting late bids. A carrier unanswered at observation cutoff is an incomplete timing observation. Pool across carriers initially, then shrink each carrier's empirical arrival and improvement estimates toward the pooled estimate. The decision uses the probability of a useful bid within the next short interval, expected gain and remaining time. Always use the real six-minute cap. Offer price and eligibility still come from deterministic pricing. With sparse data or detected drift, use the baseline.

Run the learned policy in shadow mode first. Evaluate chronologically: train only on earlier cases, predict using facts visible at decision time and compare with replay of the baseline on the same later cohort. Report sample count, improvement on fully observed candidate sets, time and deadline misses. Distinguish replay estimates from official board results. Promote only when held-out outcomes warrant it. Deliver a baseline and a measurable shadow implementation even when live data is too sparse to justify promotion.

## 8. Persistence, recovery and isolation

| Logical records | Required identity or invariant |
|---|---|
| Mailbox cursor, inbox messages, thread links, attachment blobs | Unique team plus upstream message ID. Insert messages and advance page cursor in one commit. Deduplicate bytes by hash while preserving each source attachment identity. |
| Session, request revisions, package groups, facts and evidence | Stable session ID, unique originating RFQ, monotonically increasing state version. Every price-affecting fact is attached to a revision and source. |
| Tariff documents, versions, lane rules, break rows; portal snapshots; bids and candidates | Immutable quote inputs. Store effective time and observation time separately. A late tariff can affect open work while leaving the original quote snapshot reproducible. |
| Decisions, quote snapshots, bookings, milestones and tracking questions | Decision cutoff is the last input event considered. Unique first quote per RFQ, stable team reference, unique tracking answer intent. Prevent cross-shipment joins. |
| Outbox, attempts, timers and job leases | Unique action key, next available time, bounded retry count, lease expiry and fencing token. Maintain indexes for due jobs and unsent actions. Uncertain transport outcomes are distinct from definitely failed validation. |
| Event log and frontend projections | Globally ordered committed event sequence with stable session versions. Allocate a cursor under a short transaction-held sequencer lock or equivalent commit-ordered mechanism. A plain database sequence allocated before commit can produce a skipped SSE event. |
| Gateway usage, quota state, model observations, score snapshots | Record source, as-of timestamp, actual vs estimated spend and policy version. Keep delayed scores, board freezes and provisional evidence visible. |
| Frontend idempotency records and replays | Scope keys to team, operation and resource. Store input digest, response and status. Check existing records before command version validation so a genuine retry gets its original response. Preserve for the event duration. |

Commit state transitions, outbox intents and stream events atomically. Lock per session only during short state changes. Check input revision and current control state again at dispatch. A duplicate timer or concurrent worker may recompute a decision; database constraints select one durable action. Run reconciliation for stuck leases, unmatched messages, stale candidates, uncertain deliveries and due deadlines on startup and periodically.

Use a monotonic elapsed timer for local timeouts and UTC Instants for externally meaningful times. Never use a client clock to authorize a quote. Apply bounded backoff with jitter to transient reads. The deadline and external channel rules determine write retries. Keep the database volume and attachments durable across deployment restarts.

## 9. Frontend handoff and transport contract

The separate frontend team can begin from **forwarder.openapi.json** today. It is OpenAPI 3.1.1 in JSON, with operation IDs, request/response schemas, domain enums, problem responses, synthetic examples and a typed event payload for the SSE stream. The backend must serve the exact checked-in file at /openapi.json. Serve team resources under /api/v1. Breaking changes require an explicit contract revision coordinated with the frontend.

| Frontend surface | Calls | Behavior |
|---|---|---|

| Session finder | listSessions | Combine search with phase, autonomy and verdict filters. Preserve filters when following a next-page cursor. An empty result is a successful empty page. |
| Session detail and streaming | getSession, listSessionEvents, listMessages, getAttachment, streamEvents | Show evidence-backed facts, request revision, candidate comparisons, selected basis, deadlines, pending sources, correspondence, booking and tracking. For quick setup, generate TypeScript types with **npx openapi-typescript docs/forwarder.openapi.json -o src/api/forwarder.ts** from the repository root or an equivalent frontend project path. A frontend developer can use **npx @stoplight/prism-cli mock docs/forwarder.openapi.json** to inspect static JSON responses before the Java service starts. The contract's synthetic example uses session s_100 and tariff tf_yel_nov. Use the Java demo for timed events, commands, transitions and reconnect behavior. Backend deliverable must include a short client example or curl transcript for list → detail → stream → replay.

**Authentication and stream.** The team API accepts its own bearer credential. Keep the live team UI private. Prefer a same-origin frontend proxy that attaches that token server side. For a direct browser SPA, use a team UI credential supplied at runtime and authenticated fetch streaming. Never put credentials in query parameters. Native EventSource does not set arbitrary bearer headers. The 5U team key, gateway key and model setup endpoints stay server side. Restrict development CORS origins by configuration.

**Snapshot plus stream.** Fetch a detail or dashboard snapshot, keep snapshotCursor, then connect to /api/v1/events/stream?after={cursor}. Each change frame contains a global id, event name change and JSON Event data. Heartbeats are SSE comments. Treat events as invalidations, deduplicate by sequence, update visible targets and periodically refetch summary totals. Reconnect from last applied sequence. On 410, discard the expired cursor, fetch a fresh snapshot and reconnect. Dashboard snapshot first, then list reads and stream from the dashboard cursor also covers list updates during startup. Keep cursor IDs as strings to preserve 64-bit precision in JavaScript.

**Response conventions.** Use UTF-8 JSON and camelCase. Times are RFC 3339 UTC; money and quantities are decimal strings. Omit unavailable optional properties. Empty collections are arrays. Default page size 25, maximum 100. Use opaque keyset cursors tied to sort/filter and a read boundary, keeping page membership stable while users navigate. A mismatched cursor is 400; expired is 410. Errors return application/problem+json with a stable code and requestId. Mutations are scoped to one team and require an idempotency key. Do not expose logs, raw provider errors containing secrets or arbitrary external URLs as action targets.

## 10. Simulation, observability and tests

Implement demo adapters for inbox, portal, carrier bids, gateway extraction, booking confirmations and board. Use a virtual clock and deterministic fixture IDs. Replay reads immutable facts known at each simulated instant. Start from the original sourcing timeline, apply the chosen perturbation to arrival times or source availability, then rerun scheduling, ranking and expiry against that virtual timeline. Historical late bids may become visible only at their simulated arrival time. RECORDED must reproduce the recorded action, selected candidate, amount and timestamp. Replays may save their own results but cannot enqueue live jobs, send correspondence, book, or consume paid tokens.

Record structured operational events with case, revision, decision cutoff and correlation ID. UI-visible explanations contain verifiable facts, policy reasons and elapsed times. Record successful quote latency, rejection reason, amount discrepancies where evidenced, number of candidates by source, parser fallback, ambiguous delivery, booking conversion, first tracking answers, request/tokens/cost and portal 429s. Separate estimated local indicators from official points. When loss patterns cluster, refresh affected inputs and evaluate candidate policy changes in replay. Automatically activate validated tariff data. Keep speculative policy changes in shadow mode until they outperform the baseline.

|---|---|
